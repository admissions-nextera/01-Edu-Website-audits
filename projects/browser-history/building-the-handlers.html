Step 2: Build the HTTP handlers

With History working and tested on its own, the handlers become thin: decode input if there is any, call the method, encode the output. If a handler body is getting complicated, that's usually a sign some logic leaked into the HTTP layer that belongs in history.go instead.

visitHandler

The decode-and-validate part is already written for you in the scaffold. After that:

  • Call h.Visit(req.URL).
  • Write back 200 OK with the new current URL in a currentResponse.

backHandler and forwardHandler

These both follow the same shape:

  • Call the corresponding method, which returns (string, bool).
  • If the bool is false, write an error response. Decide on the status code yourself — the spec chapter deliberately left this open. Be ready to justify your choice.
  • If true, write 200 OK with the new current URL, same shape as visitHandler.

currentHandler

The simplest one: call h.Current(), always write 200 OK. There's no failure mode here — there's always a current URL, even on a freshly started server.

historyHandler (optional)

Call h.Snapshot() and shape the three return values into whatever JSON structure you chose in the spec chapter. This handler is purely for your own visibility while testing — it's not part of the "real" simulated behavior of a browser.

A design question worth sitting with before you write the error responses

Should errorResponse ever include more than a human-readable string? Real APIs often add a machine-readable error code ("NO_BACK_HISTORY") alongside the message, so a client can branch on it without string-matching. You don't have to add this, but decide deliberately rather than by default — and if you do add it, keep it consistent across every failure case.
