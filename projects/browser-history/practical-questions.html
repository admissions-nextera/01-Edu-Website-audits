Practical questions

Small, concrete tasks against your finished server. Each should take minutes, not hours — they're meant to poke at specific corners of your implementation.

  1. Send POST /visit with an empty body (no url field at all). Does your server return 400, or does it crash, or does it silently visit an empty-string page? If it's not 400, fix it.
  2. Send POST /visit with a body that isn't valid JSON at all (e.g. just the text hello). Confirm you get a clean 400, not a stack trace or a hung connection.
  3. Call GET /current using a browser tab or curl -X POST against it (wrong method). What does the standard library's ServeMux do by default when a path exists but the method doesn't match what you registered? Confirm it matches what you'd expect.
  4. Write a short script (bash with curl, or a small Go program using net/http as a client) that fires 20 visit requests back to back in a loop, then confirm via /history that your back stack has exactly 20 entries in the right order.
  5. Manually fire two POST /visit requests at the exact same time from two separate terminals (or with & in bash to background one). Run this 20-30 times in a loop. Does /history ever come back with a stack length that doesn't match how many visits you actually sent? If you never see corruption, does that prove your locking is correct, or just that you didn't get unlucky?
  6. Add a DELETE /history endpoint (not in the original spec) that resets the server back to its starting state — empty stacks, starting URL. Decide for yourself what status code a successful reset should return.
  7. Time how long 1,000 sequential POST /visit calls take against your running server (a simple loop with time.Now() before and after is enough). Is the bottleneck your stack operations, or something else entirely? How would you find out for sure rather than guessing?
