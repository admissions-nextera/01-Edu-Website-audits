Full project specification

State

The server maintains, in memory, for a single simulated session:

  • A back stack of previously visited URLs.
  • A forward stack of URLs available to go forward to.
  • The current URL.

On startup, pick a sensible starting page (e.g. "about:blank" or "home") as the current URL, with both stacks empty.

Endpoints

POST /visit

Request body: {"url": "https://example.com"}

Behavior:

  • Push the current URL onto the back stack.
  • Set the current URL to the one in the request.
  • Clear the forward stack entirely.

Response: 200 OK with the new current URL. If url is missing or empty, 400 Bad Request.

POST /back

No body required.

Behavior:

  • If the back stack is empty, there's nowhere to go — return an error status (pick one, and be ready to explain why you picked it — see the engineering questions chapter).
  • Otherwise: push the current URL onto the forward stack, pop the back stack, and make the popped URL the new current URL.

Response: 200 OK with the new current URL, or the error status for the empty case.

POST /forward

Symmetric to /back: if the forward stack is empty, error. Otherwise push current onto the back stack, pop the forward stack, and make the popped URL current.

GET /current

Returns the current URL. Always succeeds (there's always a current URL, even at the very start).

GET /history (optional but recommended)

Returns a snapshot of the whole state — something like: 

{
  "back": ["page1", "page2"],
  "current": "page3",
  "forward": ["page4"]
}

This one isn't strictly required by the "browser" behavior, but you'll want it constantly while testing — it's the easiest way to see whether your stacks are actually doing what you think they're doing.

Response shape

Pick one consistent JSON envelope and use it everywhere, for example: 

{ "current": "https://example.com" }

for success, and something like 

{ "error": "no back history to go to" }

for failures. Consistency matters more than the exact shape — decide early and stick with it across every handler.

Concurrency requirement

An http.Server handles each incoming request on its own goroutine. That means two requests (say, two rapid clicks sent as two concurrent POST /visit and POST /back calls) could run your handler logic at the same time, both touching the same stacks. Your History type needs to protect its state so this doesn't corrupt it — this is flagged here deliberately; how you solve it is part of the exercise in the next chapters.

What's explicitly out of scope

  • No persistence — history resets when the server restarts.
  • No multiple sessions/users — one shared history for the whole server.
  • No frontend.

(Several of these show up as optional stretch goals later in the guide.)
