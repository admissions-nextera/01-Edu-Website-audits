Level up: extra features

Optional, roughly ordered from smallest to largest change. Pick whatever sounds interesting — none of these are required to consider the base project done.

History size cap

Real browsers don't keep infinite history. Add a max size to the back stack (say, 50 entries); once full, the oldest entry gets dropped when a new one is pushed. This is a small change to Visit, but it touches the question of whether a slice is still the right structure, or whether a ring buffer would fit better.

Multiple tabs / sessions

Instead of one global History, support multiple independent histories keyed by a tab or session id. This means: a way to create a new tab (POST /tabs returning an id), and every existing endpoint needs that id (as a path segment, e.g. /tabs/{id}/visit, or a header). This is the change that turns "one struct" into "a map of structs protected by its own lock" — worth thinking hard about where the locking needs to happen once there are two levels of shared state instead of one.

Persistence across restarts

Write the state to a file (JSON is fine) on every mutation, or on a timer, and load it back on startup. This connects directly back to the earlier File I/O material from the plan. A harder version: use SQLite instead of a flat file, which connects to whatever comes later in the curriculum around databases.

URL validation

Right now any non-empty string is accepted as a "URL." Add real validation — using net/url.Parse and rejecting malformed input with a proper 400 and a useful error message.

Middleware: request logging

Wrap your mux (or each handler) with a small middleware function that logs the method, path, and how long the request took. This is a natural extension of the handler-closure pattern already used in the starter scaffold — a middleware is just a function that takes a handler and returns a new one that does something extra around it.

Rate limiting

Cap how many requests a client can make per second (a simple token-bucket or fixed-window counter is enough for a first pass), and return 429 Too Many Requests once they exceed it. A good excuse to practice building something time-based and concurrent-safe from scratch.

A minimal frontend

Explicitly out of scope for the base project, but a natural next step once the API is solid: a single static HTML page with Back/Forward/Visit buttons that calls your API with fetch() and displays the current URL and both stacks. This is a good bridge into whatever frontend material comes later in the plan.
